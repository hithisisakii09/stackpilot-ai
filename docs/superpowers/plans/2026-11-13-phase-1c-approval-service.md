# Independent approval service

Start from `9939339a39ddd829c62f14aee81fb44344b8ff6a` on the existing Phase 1C branch. Implement authenticated pending-request reads, owner decisions, revocation and history using existing opaque identity handles and tenant tables.

1. Write an integration behavior test against a separate owned approval database. Record RED for authenticated request capture and independent owner approval, using real synthetic signatures and restricted connections.
2. Demonstrated migration need: claims currently have no resource version, and control role cannot read authoritative claims/products/evidence. Add migration 0003, canonical generator/manifest and real Drizzle versioned claim schema. Add positive claim version and SELECT-only review reads. Preserve SQL/manifests 0001/0002. Explicit target 3 remains opt-in. Test fresh/upgrade, pinning, idempotency and actual grants.
3. Extend identity with a registry-backed authenticated transaction bridge. Reject fake identity service objects and handles. Resolve live trust and session inside the same control transaction, hold a session share lock to serialize revocation, recheck expiry/trust before commit. Derive all organization/actor scope internally. Preserve existing session behavior and limits.
4. Implement `createApprovalService({identity})` with `createClaimRequest(handle,{requestId,agentId,claimId})`, `listPending(handle)`, `history(handle,{requestId})`, `decide(handle,{requestId,decision,expectedVersion,requestDigest})` and `revoke(handle,{requestId,expectedVersion,requestDigest})`. Authenticated request capture is needed to establish trusted requester bindings from authoritative state. Support candidate claim review only, action approve-claim. All other combinations fail closed.
5. Derive canonical payload/evidence/policy and request hashes from database and locked repository policy. Read the resource/agent/evidence snapshot in one SQL statement. Include resource version, requester, risk, action, resource identity, policy version/full locked policy and digests. No caller-supplied state establishes authority. New requests require linked candidate evidence with valid URLs/dates/digests. Review decisions leave candidate flags, executors and release gates locked.
6. Serialize per-request decisions using a transaction advisory lock, then read fresh history and authoritative state. Require same-org independent owner. Pending transitions to approved or rejected at version 1. Only approved can transition to revoked at version 2. Rejection/revocation are terminal for that request. Append immutable decision, audit and outbox atomically. Bound reads and reject incomplete legacy bindings. Future use of an approval must revalidate its bound state.
7. Tests cover all denials, forged service/owner/handle, actual app role, two tenants, self approval, reviewer/expired/revoked/trust-changed sessions, stale resource/evidence/policy/hashes, unsupported/protected actions, concurrent duplicate/conflicting decisions, terminal transitions, immutable history and rollback. Test migration parity and retained candidate/zero-budget controls. Use synthetic local fixtures only.
8. Independent review, fix reproduced findings, full existing npm test/build/data/preflight, exact-SHA Linux Chromium/axe CI and required checkpoint. Preserve untracked reports, pending PRs, hosting, protected branches and INR 0 controls. No HTTP transport/orchestration in this change.

The canonical state snapshot is the decision's consistency point. Request/binding/history writes are append-only for both application/control roles. Advisory locking serializes service decision writers. Source changes after a snapshot make that bound approval stale for subsequent use. Database session locks serialize revocation with a decision transaction. No runtime executor consumes these records.
