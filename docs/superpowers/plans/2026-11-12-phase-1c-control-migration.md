# Phase 1C next slice: forward-only control schema

Starting point: `2b52cf369fce122dd69581985860793d47784e66` on the existing Phase 1C branch. Implement step 2 of the [Phase 1C plan](2026-11-12-phase-1c-local-identity-approvals.md). No real trust provisioning, authenticated principal/session service or listener is enabled.

1. Add behavior tests to the existing real PostgreSQL harness. Observe meaningful RED for explicit target-2 migration, new tables and versioned decisions; unavailable tooling is not RED. Keep foundation tests on their target-1 database and add isolated control/failure/restore databases inside the same owned temporary cluster.
2. Preserve migration 0001 and its manifest/checksum exactly. Extend `applyMigrations(pool, {targetVersion})`, default target 1, to verify all reviewed migrations and applied ordered history before transactional DDL. Reject gaps, unknown versions, altered hashes, downgrade attempts and unknown options. Explicit target 2 applies fresh or upgrades v1; idempotent reapplication is a no-op. Serialize with the existing advisory lock. Rollback and sanitized errors retain existing behavior.
3. Create `control-schema.mjs` with canonical metadata shared by real Drizzle objects and migration 0002 SQL. Add tenant-scoped `auth_challenges`, `auth_sessions`, `approval_request_bindings`; extend approval decisions with positive version and unique (org, request, version). Preserve existing decision rows as version 1. New decisions must reference a complete matching request binding; add the FK as NOT VALID so legacy history remains readable without granting new legacy decisions. Challenge/session rows contain hashes and external public-key identifiers, never raw private credentials.
4. Use forced RLS, composite tenant FKs, indexed expiry and FK paths, bounded lifetimes (challenge <=60 seconds/session <=15 minutes), digest constraints and immutable binding/decision/audit history. Restrict updates to challenge consumption and session revocation columns only. Create `stackpilot_control` NOLOGIN and without elevated flags/memberships. Grant only required reads, auth/binding/decision inserts, audit/outbox inserts and consumption/revocation updates. Existing app role has no control-table access and still cannot write decisions. Do not enable the role for actual connections yet; trusted principal transaction adapter belongs with authenticated services.
5. Add an explicit CLI `--apply --target-version 2` path while preserving `--apply` target-1 behavior. No migration on import, build, application startup or unknown/default database. Only run against harness-owned databases in this session.
6. Test fresh/upgrade/idempotency, schema/ORM constraints and indexes, legacy history preservation, drift/gaps/downgrade, DDL rollback, RLS cross-tenant denial, app/control grant matrices, new-decision binding, uniqueness, audit rollback and dump/restore. Test control permissions using transaction-local SET ROLE from synthetic test administrator; production role stays NOLOGIN.
7. Independent security review, full existing npm test chain, clean build/preflight and exact-SHA Linux/Chromium/axe workflow. Commit/push scoped development changes only; preserve all local reports and pending PRs. Report versions, RED/GREEN, totals/skips, warnings and CI provenance. No protected branches, PR mutations, hosting/deployment changes, accounts, new dependencies or spending.

Forward recovery: roll back a failed transaction; restore the owned synthetic backup and reapply reviewed migrations. Never edit applied migration bytes or rewrite the ledger to repair real drift. No down migration drops identity/approval history.

Risks: global role collisions, migration checksum laundering, tenant escape, privileged pooled connections and authority inferred from data. Validate role flags/memberships and existing grants rather than silently adopting an unrelated role. Database records remain preparation data until real authenticated services exist.
