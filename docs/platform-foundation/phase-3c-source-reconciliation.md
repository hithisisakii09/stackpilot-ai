# Candidate source reconciliation

`openReconciliationStore(config)` uses the existing owned disposable market database gate and explicit migration target 7. The new reconciliation_links table has domain-specific tenant foreign keys, one outgoing successor per original, forced RLS and SELECT/INSERT app privileges. Default migration target remains 1. Existing strict Phase 3A/3B interfaces retain their behavior.

`store.scope(organizationId).propose({idempotencyKey,domain,fromId,toId,reason},{apply:true})` accepts market or competitor observations already stored in that tenant. Both records must describe the same subject/category/dimension/region/period. Competitors also retain vendor identity. The correction must be at least as recent and have complete current source bindings. The original can retain a changed source declaration. IDs and digests bind complete immutable observations and the reason. Requests are detached before awaiting. One existing successor, competing proposals and cycles are checked under the shared tenant transaction lock. Proposal, idempotency, audit and outbox commit or roll back together.

Links carry unreviewed candidate state. They preserve original evidence and identify a proposed correction. Independent approval for reconciliation remains a future service scope. Existing claim approvals do not grant authority over these links.

`scope.analyze({domain,selection,weights?})` takes a selection with subjectIds, featureIds, region, periodStart and periodEnd. Market selections use all three metric IDs as featureIds and require the existing positive finite weights. Competitor selections use their declared feature IDs. Up to five subjects, ten dimensions, one hundred observations and one hundred related links are accepted. Oversized snapshots fail explicitly. Proposal cycle traversal is capped at one hundred edges.

A single SQL statement reads product metadata, observations, current source bindings and candidate links. Analysis returns annotated history, proposed supersession/correction reasons, contributing link IDs, missingSubjects and deterministic digests. A current source mismatch produces stale-source-binding. This slice defines staleness through changed or missing authoritative bindings and preserves existing date validation. It introduces no independent expiry policy.

Any unresolved proposal or stale binding keeps affected declarations/scores UNKNOWN. Market history blocking is conservative across the selected subject, including historical declarations. Supported market scores retain deterministic ordering before UNKNOWN results. Comparison and per-opportunity digests include reconciliation history, links and final state. No observation is silently removed or treated as independently verified. The pure prepareReconciliation and analyzeReconciledEvidence functions validate candidate inputs and support deterministic tests.

Migration, proposal and analysis tests use synthetic evidence and owned temporary PostgreSQL clusters. Owner provisioning, authenticated operational UI, independent source review and evidence acceptance remain separate gates. The scoped checkpoint records actual test and CI evidence.
